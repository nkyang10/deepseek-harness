# Agent Note：持久的浏览器配对与可撤销会话

Status: implemented

[English](2026-10-17-durable-browser-pairing.md) | 中文

## Problem

Desktop 的 Web 监听默认对局域网服务，以便手机访问 GUI（[可配置的 Web 绑定](../../../../docs/upgrade-guide/v0.2.1-alpha.2/browser-pairing-sessions/guide.zh.md)）。这让浏览器启动令牌成为可分享的产物，而该令牌每次 Host 启动都会重新生成。因此交给手机的链接会在下次应用重启时失效，且没有任何信号：浏览器收到的是与地址写错时一模一样的 `401`，而 Desktop 的 401 正文还让用户去“打开 `dsh web` 打印的 URL”——那个 CLI 并没有在运行。两位操作者共享一个链接后，既无法看到当前有哪些浏览器已连接，也无法切断其中之一。

令牌当初是按**进程**凭据设计的，每进程轮换正是其要点：泄露的 URL 会随应用重启而失效。保持这一性质与让链接持久，是直接冲突的，因此真正的决策是产品应当承诺哪种有效期。

## Decision

凭据被拆分为**持久配对码**与**按设备的会话**，两者与 cookie 签名密钥一起存放在既有的 `client-connection/browser-session` grant 记录中。

配对码持久有效，直到它的所有者主动更换。`authenticatedUrl()` 放入查询串的就是它，“复制网页链接”复制的也是它，因此分享出去的链接可跨重启继续配对——这正是本次改动要消除的故障。`ctx.connection.rotatePairingCode()` 负责替换它，这是为流传过远的链接准备的出口；它与撤销刻意分开，因为泄露的**配对码**和多余的**设备**是两个不同的问题。

每个交换配对码的浏览器都会成为一个 `BrowserSession`，带有各自不透明的 `BrowserDeviceId`；签名 cookie 指明该会话，而不再自行携带有效期。于是会话表成为“谁能与 Host 对话”的权威：`revokeBrowserSession(id)` 删掉一行，于是指明它的每个 cookie 立即停止通过验证，而其他会话与配对码不受影响。Desktop 通过“已配对设备…”暴露这一能力，列出每个浏览器配对时提供的 `User-Agent` 与配对时间，并在撤销前确认。

对同一 authority 已持有会话的浏览器再次配对时，会沿用其身份与配对时间，只刷新过期时间，因此重新打开链接不会堆积孤立记录。

同一配对路径也接受由所有者配置、显示在所服务登录页上的**口令**。匹配的表单 POST 会铸造一个普通的按设备会话 cookie，因此口令只决定谁可以配对，而不是认证一个长期主体；撤销仍然按设备进行。由于口令由人选择，其 POST 在浏览器认证之前先通过 Host/Origin 校验；WebView 或沙箱页面可能以不透明的 `null` Origin 提交该表单，口令 POST 在通过 Host 栅栏后接受它，而 `/api` 请求仍拒绝不透明 Origin。失败次数按直连对端地址计数，连续第十次失败会将该对端封禁一分钟。所有者通过设置页写入十二到一千零二十四个字符的口令，设置页只在 `client-connection/passcode-verifier` grant 记录中写入加盐 scrypt 校验记录；口令本身从不持久化，持久配对链接与它并存。校验记录固定的代价参数会被精确校验，畸形记录会响亮失败。

`authorizeIndex` 是异步的，因为一次成功的口令提交要先派生密钥，而一次成功的配对要先写入会话，之后二者才能铸造 cookie。这传导到 `serveStatic` 与实验性 inspector 的 DevTools 路由，两者本来就在异步处理函数内。

## Consequences

- **配对码比进程活得久，因此暴露也比进程活得久。** 256 位不可猜测的配对码足以抵御暴力破解；真正的风险是分享，这正是配对码可轮换、且它配对的每个设备都可撤销的原因。没有加入尝试次数限制：那会给 index 请求路径增加状态，去防御配对码熵值已经排除的威胁。
- **`lastSeenAt` 先在内存中发布。** 请求认证是同步的，不能等待凭据文件，因此一次活动标记会更新内存表，持久写入发生在下一次配对、撤销、轮换或 `listBrowserSessions()` 时——后者是该值的唯一消费方。`persist()` 通过取文件值与本次激活值中较新者，把这些观察结果向前合并，因此另一个进程的并发结构性改动不会被覆盖。
- **此前存在的每个 cookie 都停止通过验证。** 旧 payload 不指明任何设备，接纳它就意味着保留第二条认证路径。该记录的签名密钥在升级中保留，配对码与空表会一并写入，因此唯一可见的效果就是重新配对。
- **已配对的浏览器仅凭它呈现的内容来识别。** `User-Agent` 是 Host 拥有的唯一人类可读事实，因此两个具有相同该字符串的浏览器在列表中无法分辨。更丰富的身份需要浏览器证明什么，而明文 HTTP 配对无法提出这种要求。
- **口令是低熵凭据，猜测窗口有界。** 每个直连对端地址连续十次失败后会被封禁一分钟；成功提交会清零计数。分布式攻击者不受单一地址限制，因此把口令暴露到可信网络之外时，部署仍依赖 TLS 与口令本身的长度。存储的校验记录使用固定的 scrypt 代价参数（N=65536、r=8、p=2）、16 字节盐与 32 字节派生密钥；被窃取的凭据记录无法当作口令重放，畸形记录会响亮失败，而不会接受攻击者选择的参数。登录页带有禁止脚本与框架的 CSP 及 no-referrer，其标记只包含固定的错误标记。

## Alternatives considered

**保留每进程令牌并接受链接失效。** 成本最低，也确实是最初的实现。否决：用户唯一的补救是找到一个没有任何地方显示的 URL，而且该故障与地址写错无法区分。

**由浏览器输入、无需配对即可认证每个请求的固定共享口令。** 用户熟悉，但它授予任何知道口令的人长期访问权，且无法提供可撤销的按设备身份。已实现的口令避开了这种形态：它只开启配对交换，因此正确提交仍会铸造可撤销的按设备会话。其由人选择的低熵正是表单 POST 需要信任栅栏与失败限流的原因。

**滑动过期，每次请求刷新。** 可以让活跃浏览器无限期保持登录。否决：无界的会话有效期与 `cookieMaxAgeDays` 相抵触，而其绝对有效期语义是先前决策确定的。

**不持久化会话表，仅由 cookie 过期推导存活状态。** 可以省掉上面的合并逻辑。否决：没有持久列表就无法撤销，而撤销正是本次改动存在的理由。
